\subsection{System Architecture}
\label{subsec:system-architecture}

The Solar Energy Monitoring and Control System implements a modular monolithic architecture with clear layer separation. The architecture is designed for maintainability, security, and operational simplicity while supporting real-time data processing and monitoring requirements.

\paragraph{Layer Descriptions}

\begin{itemize}
    \item \textbf{Presentation Layer}: Next.js-based web application providing separate portals for administrators and customers. Uses REST APIs for data operations and WebSocket for real-time updates.
    \item \textbf{Application Layer}: Spring Boot backend implementing business logic in five functional modules (User Management, Energy Monitoring, Payment Compliance, Tampering Detection, Service Control). Exposes RESTful APIs and WebSocket endpoints.
    \item \textbf{Persistence Layer}: PostgreSQL relational database managing all system data with JPA entity mappings. H2 in-memory database used for development and testing.
\end{itemize}

\paragraph{Key Module Methods (Input → Output → Action)}

This section describes the main methods of important classes and controllers, specifying their inputs, outputs, and primary actions:

\textbf{User Management Module:}
\begin{itemize}
    \item \texttt{AuthController.register(RegisterRequest)} → \texttt{AuthResponse}: Validates user data, hashes password with BCrypt, creates User entity, saves to database, generates JWT token.
    \item \texttt{AuthController.login(LoginRequest)} → \texttt{AuthResponse}: Authenticates credentials, checks account status, updates last login timestamp, generates JWT token.
    \item \texttt{UserService.updateProfile(Long userId, ProfileUpdateRequest)} → \texttt{UserDTO}: Validates update data, checks email uniqueness if changed, updates User entity, returns DTO.
    \item \texttt{SecurityService.hasAccessToInstallation(Long installationId)} → \texttt{boolean}: Checks if current authenticated user is admin or owns the installation.
\end{itemize}

\textbf{Energy Monitoring Module:}
\begin{itemize}
    \item \texttt{EnergyDataController.submitReading(EnergyDataRequest)} → \texttt{EnergyDataDTO}: Validates installation access, creates EnergyData entity, persists to database, publishes WebSocket update to \texttt{/topic/installation/\{id\}/energy-data}, returns DTO.
    \item \texttt{EnergySummaryService.generateDailySummary(Long installationId, LocalDate date)} → \texttt{EnergySummaryDTO}: Queries all energy readings for date, calculates total generation/consumption, computes efficiency, creates EnergySummary entity, saves and returns DTO.
    \item \texttt{SolarInstallationService.updateStatus(Long id, InstallationStatus status)} → \texttt{SolarInstallationDTO}: Updates installation status, publishes WebSocket status update, logs operational change.
\end{itemize}

\textbf{Payment Compliance Module:}
\begin{itemize}
    \item \texttt{PaymentService.makePayment(Long userId, MakePaymentRequest)} → \texttt{PaymentDTO}: Validates user owns installation, finds pending payment, marks as PAID, updates payment plan remaining amount, creates payment record, triggers service restoration if applicable, returns DTO.
    \item \texttt{PaymentPlanService.createPlan(Long installationId, PaymentPlanRequest)} → \texttt{PaymentPlanDTO}: Calculates installment amount, generates payment schedule, creates PaymentPlan and Payment entities, saves all, returns DTO.
    \item \texttt{PaymentReminderService.dispatchReminders()} → \texttt{void}: Queries upcoming due payments, checks reminder configuration, creates and sends email reminders for each qualifying payment.
\end{itemize}

\textbf{Tampering Detection Module:}
\begin{itemize}
    \item \texttt{TamperEventService.createEvent(Long installationId, TamperEventRequest)} → \texttt{TamperEventDTO}: Creates TamperEvent entity, sets severity and confidence score, marks installation as tampered, creates SecurityLog entry, publishes WebSocket alert to \texttt{/topic/installation/\{id\}/tamper}, returns DTO.
    \item \texttt{SecurityLogService.logActivity(Long installationId, SecurityActivityRequest)} → \texttt{SecurityLogDTO}: Creates SecurityLog entity with timestamp and activity type, persists to database.
\end{itemize}

\textbf{Service Control Module:}
\begin{itemize}
    \item \texttt{ServiceStatusController.suspendForPayment(Long installationId, String reason)} → \texttt{ServiceStatusDTO}: Checks authorization, updates ServiceStatus to SUSPENDED, creates OperationalLog, sends device command via DeviceCommandService, returns DTO.
    \item \texttt{DeviceCommandService.sendCommand(Long installationId, DeviceCommandRequest)} → \texttt{DeviceCommandDTO}: Creates DeviceCommand entity with status PENDING, persists, publishes command for device consumption, returns DTO.
    \item \texttt{PaymentIntegrationService.handlePaymentCompleted(Payment payment)} → \texttt{void}: Listens for payment events, checks if service suspended due to payment, triggers service restoration if applicable.
\end{itemize}

\subsubsection{Module Communication}
\label{subsubsec:module-communication}

Modules communicate through:
\begin{itemize}
    \item \textbf{Direct Service Injection}: Controllers inject services from other modules when synchronous operations are needed (e.g., SecurityService used by multiple controllers for authorization).
    \item \textbf{Spring Application Events}: Asynchronous notifications between modules (e.g., PaymentEventPublisher publishes payment events consumed by PaymentIntegrationService).
    \item \textbf{Shared Entities}: Modules share entities through JPA relationships (e.g., Payment references SolarInstallation, TamperEvent references SolarInstallation).
    \item \textbf{WebSocket Broadcasting}: Real-time updates pushed to frontend via WebSocketService on topics \texttt{/topic/installation/\{id\}/energy-data}, \texttt{/topic/installation/\{id\}/status}, \texttt{/topic/installation/\{id\}/tamper}.
\end{itemize}

\paragraph{Relationships}
\begin{itemize}
    \item \texttt{users} 1→* \texttt{solar\_installations}: One user owns multiple installations
    \item \texttt{solar\_installations} 1→* \texttt{energy\_data}: One installation generates many readings
    \item \texttt{solar\_installations} 1→* \texttt{payments}, \texttt{tamper\_events}, \texttt{service\_status}: Installation is the central entity
    \item \texttt{payment\_plans} 1→* \texttt{payments}: Plan contains multiple scheduled payments
    \item \texttt{payments} 1→* \texttt{payment\_reminders}: Payment can have multiple reminders
    \item \texttt{tamper\_events} 1→* \texttt{tamper\_responses}: Event can trigger multiple responses
    \item \texttt{solar\_installations} 1→1 \texttt{alert\_configs}, \texttt{monitoring\_status}, \texttt{grace\_period\_configs}: One-to-one configuration relationships
\end{itemize}

\paragraph{Database Constraints and Indexes}
\begin{itemize}
    \item \textbf{Primary Keys}: All tables use auto-incrementing BIGSERIAL (PostgreSQL) or IDENTITY (H2)
    \item \textbf{Foreign Keys}: CASCADE delete not used; referential integrity maintained at application layer
    \item \textbf{Unique Constraints}: \texttt{users.email}, \texttt{alert\_configs.installation\_id}, \texttt{grace\_period\_configs.installation\_id}
    \item \textbf{Composite Index}: \texttt{energy\_data(installation\_id, timestamp)} for time-range queries
    \item \textbf{Recommended Additional Indexes}: \texttt{payments(installation\_id, due\_date)}, \texttt{service\_status(installation\_id, status)}, \texttt{tamper\_events(installation\_id, resolved)}
\end{itemize}

\section{Implementation}
\label{sec:implementation}

This section documents the actual implementation decisions made during development, focusing on frameworks, patterns, code structure, error handling, and deployment. All content reflects the implemented codebase.

\subsection{Implementation Decisions}
\label{subsec:implementation-decisions}

\subsubsection{Framework and Technology Selection}
\label{subsubsec:component-justification}

\paragraph{Backend: Spring Boot 3.3.4 with Java 21}
Selected for comprehensive security (Spring Security with JWT), data access (Spring Data JPA), and WebSocket support. Java 21's modern features (records for DTOs, enhanced pattern matching) reduce boilerplate while maintaining enterprise stability. Spring Boot's auto-configuration minimizes configuration overhead.

\paragraph{Frontend: Next.js 15 with React 19 and TypeScript}
Next.js App Router provides file-based routing and server-side rendering capabilities. TypeScript ensures type safety across the entire frontend and enforces contracts with backend DTOs. React 19's concurrent rendering improves performance for real-time energy data displays.

\paragraph{Database: PostgreSQL 15 (Production) and H2 (Development/Testing)}
PostgreSQL provides ACID compliance for payment transactions and excellent performance for time-series energy data queries. H2 in-memory database enables fast test execution without external dependencies. JPA entity-first approach generates schema from annotated Java classes.

\paragraph{Real-time Communication: STOMP over WebSocket}
WebSocket with STOMP protocol enables pub/sub model for energy readings, tamper alerts, and installation status changes. Spring WebSocket provides seamless integration. SockJS fallback ensures browser compatibility.

\paragraph{Authentication: JWT with BCrypt Password Hashing}
JWT tokens enable stateless authentication suitable for horizontal scaling. BCrypt (configured for 12 rounds) provides cryptographically secure password hashing. Role claims (ADMIN, CUSTOMER) embedded in token payload enable authorization decisions without database queries.

\subsubsection{Data Representation and Persistence}
\label{subsubsec:data-representation}

\paragraph{Entity Design Patterns}
\begin{itemize}
    \item \textbf{Temporal Data}: \texttt{LocalDateTime} used consistently to avoid timezone complications. Energy readings store both instantaneous measurements (watts) and cumulative totals (kWh).
    \item \textbf{Monetary Values}: \texttt{BigDecimal} with scale of 2 for all currency amounts prevents floating-point precision errors in payment calculations.
    \item \textbf{Enum Types}: Java enums (e.g., \texttt{InstallationStatus}, \texttt{PaymentStatus}) mapped to VARCHAR columns provide type safety and refactoring support.
    \item \textbf{Relationship Mapping}: Unidirectional \texttt{@ManyToOne} relationships with \texttt{FetchType.LAZY} to avoid N+1 query issues and circular serialization.
    \item \textbf{Cascade Strategy}: Manual entity lifecycle management rather than JPA cascades to prevent unintended data loss.
\end{itemize}

\paragraph{Code Patterns and Conventions}
\begin{itemize}
    \item \textbf{Architecture}: Controller-Service-Repository pattern with clear separation of concerns. Controllers handle HTTP, services contain business logic, repositories manage data access.
    \item \textbf{Package Organization}: Feature-based modules (\texttt{user\_management}, \texttt{energy\_monitoring}, \texttt{payment\_compliance}, etc.) rather than layer-based packaging.
    \item \textbf{Naming}: PascalCase classes, camelCase methods/variables, UPPER\_SNAKE\_CASE constants, snake\_case database columns.
    \item \textbf{Java Features}: Records for DTOs, Lombok annotations (\texttt{@Data}, \texttt{@Builder}) for entities, \texttt{Optional} for nullable returns, Stream API for collections.
    \item \textbf{TypeScript Features}: Interface definitions for all API types, generic \texttt{Page<T>} wrappers, async/await for API calls, custom hooks for reusable logic.
\end{itemize}

\subsection{Code Organization and Quality Practices}
\label{subsec:code-quality}

\subsubsection{Module Structure}
\label{subsubsec:code-structure}

The backend follows a feature-based package structure where each functional module (\texttt{user\_management}, \texttt{energy\_monitoring}, \texttt{payment\_compliance}, \texttt{tampering\_detection}, \texttt{service\_control}) contains its own controllers, services, repositories, entities, and DTOs. This organization supports clear boundaries between concerns and facilitates testing in isolation.

Each module implements the Controller-Service-Repository pattern:
\begin{itemize}
    \item \textbf{Controllers} handle HTTP requests/responses, parameter validation, and security annotations
    \item \textbf{Services} implement business logic and transaction management
    \item \textbf{Repositories} extend Spring Data JPA interfaces for database access
\end{itemize}

Frontend code is organized by feature within the \texttt{app/} directory (Next.js App Router), with shared components in \texttt{components/}, API clients in \texttt{lib/api/}, and reusable hooks in \texttt{hooks/}.

\subsubsection{Code Reusability Mechanisms}
\label{subsubsec:code-reusability}

Cross-module functionality is shared through:
\begin{itemize}
    \item \textbf{Security Service}: Authorization logic (\texttt{hasAccessToInstallation()}) injected across controllers
    \item \textbf{WebSocket Service}: Centralized broadcast methods for real-time updates
    \item \textbf{Event Publishers}: Spring Application Events decouple modules (e.g., payment completion triggers service restoration)
    \item \textbf{Custom Hooks}: Frontend hooks like \texttt{useAuth()}, \texttt{useWebSocket()}, \texttt{useApiRequest()} extract common patterns
\end{itemize}

No generic base classes or complex inheritance hierarchies were introduced. Services remain concrete implementations, prioritizing clarity over premature abstraction.

\subsection{Error Handling and Validation}
\label{subsec:error-handling}

\subsubsection{Input Validation}
\label{subsubsec:validation-strategy}

Bean Validation (JSR-303) annotations on request DTOs provide declarative validation:
\begin{itemize}
    \item \texttt{@NotNull}, \texttt{@NotBlank} ensure required fields are present
    \item \texttt{@Email} validates email format
    \item \texttt{@Size}, \texttt{@Min}, \texttt{@Max} constrain string lengths and numeric ranges
    \item \texttt{@Pattern} enforces regex patterns for fields like phone numbers
\end{itemize}

The \texttt{@Valid} annotation on controller method parameters triggers automatic validation before method execution. Validation failures return HTTP 400 with field-level error details.

Authorization is enforced through:
\begin{itemize}
    \item \textbf{Method Security}: \texttt{@PreAuthorize("hasRole('ADMIN')")} annotations on admin-only endpoints
    \item \textbf{Resource Ownership}: \texttt{SecurityService.hasAccessToInstallation()} verifies users can only access their own data (or all data if admin)
\end{itemize}

\subsubsection{Exception Handling Implementation}
\label{subsubsec:exception-handling}

A \texttt{GlobalExceptionHandler} class annotated with \texttt{@RestControllerAdvice} centralizes error responses:
\begin{itemize}
    \item \texttt{MethodArgumentNotValidException} → HTTP 400 with field error map
    \item \texttt{BadCredentialsException} → HTTP 401 with generic authentication failure message
    \item \texttt{ResourceNotFoundException} (custom exception) → HTTP 404 with specific error message
    \item \texttt{AccessDeniedException} → HTTP 403 with permission denied message
    \item \texttt{AuthenticationException} subtypes → HTTP 401 for authentication failures
    \item \texttt{RuntimeException} → HTTP 500 with sanitized message (no stack traces exposed to clients)
\end{itemize}

This implementation is located in \texttt{src/main/java/com/solar/exception/GlobalExceptionHandler.java} and handles exceptions consistently across all endpoints.

\subsection{Deployment Architecture}
\label{subsec:physical-components}

\subsubsection{Containerization}
\label{subsubsec:component-deployment}

The system uses Docker containers orchestrated via Docker Compose (\texttt{compose.yaml}):

\paragraph{Backend Container}
Multi-stage Dockerfile builds the Spring Boot application:
\begin{itemize}
    \item \textbf{Build Stage}: \texttt{eclipse-temurin:21-jdk} image runs Maven build
    \item \textbf{Runtime Stage}: \texttt{eclipse-temurin:21-jre} minimal JRE image
    \item \textbf{Port}: 8080 for HTTP and WebSocket connections
    \item \textbf{Configuration}: Environment variables for database URL, credentials, JWT secret
\end{itemize}

\paragraph{Frontend Container}
Separate Dockerfile builds the Next.js application:
\begin{itemize}
    \item \textbf{Base Image}: \texttt{node:20-alpine}
    \item \textbf{Build}: Next.js production build with static optimization
    \item \textbf{Port}: 3000 for HTTP
    \item \textbf{Configuration}: \texttt{NEXT\_PUBLIC\_API\_URL} environment variable
\end{itemize}

\paragraph{Database Container}
\begin{itemize}
    \item \textbf{Image}: \texttt{postgres:latest} from Docker Hub
    \item \textbf{Port}: 5432 (mapped to host port 5433 to avoid conflicts)
    \item \textbf{Persistence}: Named volume \texttt{postgres-data} for data persistence
    \item \textbf{Health Check}: \texttt{pg\_isready} command ensures database availability before backend starts

\end{itemize}

The \texttt{compose.yaml} defines service dependencies ensuring database starts before backend, and backend before frontend. No reverse proxy (nginx) is included in the current compose configuration.

\subsection{Testing Observations}
\label{subsec:lessons-learned}

\subsubsection{Test-Driven Improvements}
\label{subsubsec:testing-changes}

Writing tests revealed several design issues that were corrected:

\paragraph{Module Decoupling}
Test isolation difficulties highlighted tight coupling between payment and service control modules. Introduction of Spring Application Events (\texttt{PaymentEventPublisher} / \texttt{PaymentIntegrationService}) decoupled these modules, allowing independent testing with event mocks.

\paragraph{Entity Serialization Issues}
Controller tests exposed circular JSON serialization when entities referenced bidirectional relationships. Solution was to introduce DTOs (Data Transfer Objects) for all API responses, explicitly mapping only required fields. This pattern is now followed consistently across all modules.

\paragraph{Exception Clarity}
Generic exception messages (\texttt{RuntimeException}, \texttt{IllegalArgumentException}) made test failures difficult to diagnose. Creation of domain-specific exceptions (\texttt{ResourceNotFoundException}, custom validation exceptions) with detailed messages improved test debuggability and API error responses.

\paragraph{Test Data Management}
Repository tests initially used random data generation leading to intermittent failures. Adoption of builder patterns and fixed test data improved test reliability and readability.

\subsection{Performance and Scalability Considerations}
\label{subsec:scalability-analysis}

\subsubsection{Design for Expected Load}
\label{subsubsec:high-volume-ingestion}

The system is designed as a research prototype for small-scale deployment (approximately 10-100 installations). Performance characteristics under this expected load:

\paragraph{Energy Data Ingestion}
Raspberry Pi simulators send energy readings approximately every 18 seconds per installation. At 100 installations, this represents ~480,000 readings per day or 5-6 requests/second sustained throughput. Spring Boot's embedded Tomcat with default configuration (200 max threads) handles this load pattern without tuning.

\paragraph{Database Indexing}
Composite index on \texttt{energy\_data(installation\_id, timestamp)} is critical for time-range queries used by monitoring dashboards. Without this index, queries for 24 hours of readings would require full table scans. Repository tests validate index effectiveness using \texttt{@DataJpaTest} with H2.

\paragraph{WebSocket Scalability}
Real-time energy updates use STOMP over WebSocket. Spring WebSocket handles concurrent connections within a single JVM instance. For scaling beyond approximately 1000 concurrent connections, a message broker (Redis, RabbitMQ) would be recommended to distribute load.

\subsubsection{Known Limitations}
\label{subsubsec:database-performance}

\paragraph{Research Prototype Constraints}
As a thesis implementation, certain production optimizations were omitted:
\begin{itemize}
    \item No load testing (JMeter, Gatling) was performed to establish precise throughput limits
    \item No caching layer (Redis, EhCache) for frequently-accessed reference data
    \item No database connection pool tuning beyond Spring Boot defaults
    \item No horizontal scaling (load balancing, clustering) implementation
    \item No CDN or static asset optimization for frontend
\end{itemize}

\paragraph{Future Scalability Enhancements}
Production deployment at larger scale would require:
\begin{itemize}
    \item Read replicas for reporting and analytics queries
    \item Distributed message broker for WebSocket at scale
    \item Application-level caching for installation metadata and user profiles
    \item Time-series database (TimescaleDB, InfluxDB) for long-term energy data retention
    \item Asynchronous job processing (Spring Batch, Quartz) for background tasks like payment reminder dispatch
\end{itemize}

\subsection{Correctness and Validation}
\label{subsec:correctness-evaluation}

\subsubsection{Test-Verified Correctness}
\label{subsubsec:business-logic-validation}

Business logic correctness is validated through automated tests:
\begin{itemize}
    \item \textbf{Payment Calculations}: Service layer tests verify payment plan amortization, installment amounts, and late fee calculations using known input/output pairs
    \item \textbf{Energy Aggregation}: Repository tests validate daily/weekly/monthly summary generation against sample data sets
    \item \textbf{Authorization Logic}: Controller and service tests verify role-based access (ADMIN vs CUSTOMER) and resource ownership checks
    \item \textbf{State Transitions}: Service tests validate installation status changes (ACTIVE → SUSPENDED → ACTIVE) and prevent invalid transitions
\end{itemize}

\subsubsection{Data Integrity}
\label{subsubsec:data-integrity-validation}

Database constraints and JPA validation ensure data integrity:
\begin{itemize}
    \item Foreign key constraints prevent orphaned records (enforced by PostgreSQL)
    \item Bean Validation annotations (\texttt{@NotNull}, \texttt{@Min}, \texttt{@Max}) enforce input constraints
    \item \texttt{@Transactional} annotations ensure atomic operations (e.g., payment processing updates both \texttt{Payment} and \texttt{PaymentPlan} tables atomically)
\end{itemize}

Repository tests with \texttt{@DataJpaTest} verify these constraints work as expected.
